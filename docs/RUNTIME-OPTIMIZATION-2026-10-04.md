# 架构、并发与性能优化（2026-10-04）

本轮以可复现请求次数、事件循环延迟和计算耗时为依据，在现有接口上优化共享能力。没有引入框架、运行时依赖或修改核心仓库。

## 改动及正确性

### 玩家数据请求与缓存失效

`utils/player/service.py` 继续提供获取、读取、失效三个入口。按 UID 将“检查磁盘缓存 → 网络请求 → 成功回写”放进同一把异步锁，等待者在锁内重新检查缓存；不同 UID 并行。同 UID 的 8 个冷缓存查询由 8 次接口请求减少为 1 次。

失效操作使用同一把锁，修复“签到清缓存期间，较早发起的请求完成后又写回旧数据”。清理磁盘文件移到工作线程。锁用弱引用表，只在正在执行/等待的调用持有，不随着历史 UID 数量不断积累。

`force=True` 仍明确请求新数据；网络错误不当成成功缓存。此合并针对同进程的成功缓存场景，不承诺多进程之间去重，也不将错误长期缓存。

### 磁盘存储职责收拢

原来的干员、物品、皮肤、藏品、公招索引从 `_table_cache` 导入私有同步文件读写函数，下载策略与通用存储混在一起。

现在纯 JSON 读写统一使用 `disk_cache.read_json/write_json`：后台线程读写，唯一临时文件与原子替换，保持原有磁盘 JSON 格式。包装缓存、校验器旁车与普通 JSON 共用同一原子写入实现。`_table_cache` 专注上游下载、条件请求与表缓存。

源表覆盖判断也放入存储模块，避免皮肤/藏品索引为了文件时间判断而依赖干员业务模块。干员模块保留原别名供已有调用兼容。

检查中发现藏品索引只检查源表 TTL，没有比较索引与源表的新旧。源表刷新后仍会显示旧藏品。已复现并加入源表覆盖判断，使藏品行为与其他索引一致。

### 图片处理

背景图解码、缩放、WebP 编码及写文件移到 `asyncio.to_thread`，避免上传背景阻塞其他命令。唯一临时文件成功写完才替换目标；修复磁盘写入失败破坏原背景的问题，失败清理临时文件。

`gather_b64` 在单次调用中按 key 去重并发获取，再映射回原输入顺序。重复干员头像/图标不再反复下载或解码；空 key 和失败回退语义保持不变。没有增加跨请求的无限内存图片缓存。

### 概率算法

六星概率在 98 垫刀时达到 100%，更高状态与之等价。因此 DP 状态数组最多 99 项，不再随着计算抽数扩大。每个状态的六星概率预计算一次；每轮先汇总六星概率质量，再分配 UP/陪跑/其他六星，减少重复转移。

检查发现已有垫刀大于计算范围时，旧数组可能不够容纳继续未出六星后的状态：例如垫刀 50、再计算 5 抽，后几抽会被钳在较低概率。修复后的大小取 `min(99, start_pity + max_pulls + 1)`，独立短路径枚举测试覆盖该情形以及多目标/陪跑。

规划入口对 300 抽单目标表增加最多 64 项的 LRU，缓存不可变 tuple，只含概率参数，不缓存账号信息；公开 `build_up_table` 仍返回独立可变列表。独立数学模型继续验证概率一致性，不以优化前的错误结果当唯一标准。

## 基准结果

同一脚本、同一解释器，以临时目录和模拟 HTTP 测量。原始测量数据保留在本地基准记录中，未随仓库分发。改动后最终一次测量单独运行，没有与全量测试并发。

| 场景 | 改动前 | 改动后 |
| --- | ---: | ---: |
| 同 UID 的 8 个并发查询，上游请求数 | 8 | 1 |
| 300 抽概率表计算中位耗时 | 17.237 ms | 1.795 ms |
| 1200 抽概率表计算中位耗时 | 77.062 ms | 9.463 ms |
| 同参数重复规划中位耗时 | 14.923 ms | 0.002 ms |
| 背景转换总耗时 | 335.808 ms | 299.411 ms |
| 背景转换期间事件循环最大心跳间隔的中位值 | 335.881 ms | 3.381 ms |
| 10000 项 JSON 索引连续读 30 次，总耗时 | 146.127 ms | 125.041 ms |
| 同一索引读取场景事件循环最大心跳间隔 | 146.181 ms | 26.144 ms |

这些是受控场景，不是生产网络端到端提速。线程转移主要减少事件循环阻塞；Python JSON 解析仍受 GIL 影响，不能称为零阻塞。图片大小为确定性生成的 2048×2048 灰度 PNG；索引规模用于放大对比，不声称等于每个线上索引大小。

复跑：在插件根目录使用 GsCore 虚拟环境执行 `python tools/benchmark_runtime.py`。脚本不读取线上账号，不发真实消息。
