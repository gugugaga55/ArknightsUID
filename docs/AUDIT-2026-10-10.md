# GsCore 接入、数据完整性与测试复查（2026-10-10）

本轮基于当前工作区检查，保留全部既有未提交改动，按核心接入、数据链路和测试质量三条线复查并修复。

结论：当前插件与本机 **GsCore 0.10.5** 的接入方式兼容，本轮修复四处业务缺陷和两处测试缺口。测试与公开源检查通过，但不能据此断言所有私人接口、字段和图片均已完整准确验证。

## GsCore 规范依据

以本机 GsCore 的插件骨架，以及 `sv.py`、`handler.py`、`server.py`、`data_store.py`、配置与 ORM 的真实实现为依据。

- 嵌套包、`__nest__.py`、内层 `Plugins` 和业务 `SV` 符合核心加载流程；真实核心普通导入及嵌套加载测试通过。
- 配置、资源路径、ORM 和定时任务沿用核心接口；本轮没有修改父核心。
- 别名现在复用核心目标 SV 的鉴权，并通过核心启动钩子在数据库就绪后安装。
- 项目使用自己的 Ruff 配置（88 列、允许 E402 等），检查通过不代表逐项采用父仓库的全部格式规则。
- 别名仍依赖核心内部的 `SL`、`Trigger`、`modify_func` 和 `_sv_authorized`。当前安装版本已验证，未来核心内部接口变化仍需复测，未添加猜测性的版本兼容层。

## 本轮修复

| 问题 | 原有影响 | 最小修复与回归 |
| --- | --- | --- |
| 指令别名直接调用目标 handler，绕过目标 SV 检查 | 普通用户可能经别名执行管理员命令；禁用状态、黑白名单及私群限制失效 | 调用真实核心 `_sv_authorized`，沿用目标服务限制；回归经过核心授权、排序和 Trigger 包装链，覆盖允许及拒绝场景 |
| 别名在导入时创建无顺序保证的任务 | 数据库未就绪或同步导入时注册延迟，核心先匹配命令再执行首消息安装，首条别名可能遗漏 | 冷启动在核心建表后的 `on_core_start_before` 阶段安装；热重载通过 `on_core_start(priority=10)` 在插件 priority=0 迁移后重放；移除导入时任务，保留幂等与已有消息重试；覆盖三类钩子 |
| 公招分页未完或解析丢成员仍写入完整池缓存 | 漏掉低星干员后可能错误计算标签保底，残缺池持续缓存一天 | 明确存在 continuation 或解析成员数不足时拒绝替换缓存，复用原有旧缓存；覆盖有/无缓存及正常更新 |
| 抽卡日志保存失败仍提交补拉游标 | 后续补拉跳过未保存历史，终页还可能清掉检查点 | 日志保存返回成功状态，成功后才更新/清理游标；失败保留旧进度并提示仅供展示；覆盖写盘失败后恢复重拉 |
| 公开头像检查忽略 `hasMore=true` | 部分目录被实网检查器报告为完整成功 | 两个头像源均将显式续页标记判为失败，回归核对检查器输出和退出结果 |
| 离线测试仅拦截测试阶段的异步 HTTP | 同步 HTTP、直接 TCP 和收集阶段可能绕过限制 | 测试辅助函数拦截默认同步/异步 HTTP 与 socket connect/connect_ex，并在收集及 teardown 核对尝试记录；保留 MockTransport，覆盖异常被业务吞掉的情形 |

生产修改集中在 `arknightsuid_alias/__init__.py`、`utils/gamedata/recruit.py`、`utils/hypergryph/gacha.py`。其余为对应回归、测试设施、公开源检查器和说明文档；没有新增运行时依赖、通用事务层、重试框架或缓存层。

公招处理是拒收不完整池，**没有实现上游分页续拉**。本次实网返回 160 名且无续页；若未来真实触达分页，应根据确认后的协议补续拉。

## 仍未覆盖的边界

- 真实账号的登录、好友、抽卡历史和个人进度未实号联调。合成响应与故障注入证明调用逻辑，不能证明真实服务的全部包装、分页或刷新行为。
- 字段存在不证明值正确、服务端记录完整或 CDN 最新；尚无全表官方总量、版本/校验和及跨表引用的独立对照。
- 图片被模拟的模板测试验证上下文契约，不证明真实素材、浏览器渲染和视觉质量。
- 网络限制是进程内测试措施；独立子进程不会自动继承 monkeypatch，也不是操作系统级断网。收集前的第三方插件、DNS/UDP 和原生传输不在保证范围。
- 热重载会在后台重新运行启动钩子，过渡窗口仍可能接收消息；不能将冷启动顺序保证推广到整个重载窗口。
- 抽卡修复保证日志写入失败时不推进补拉进度，不提供多文件崩溃原子性，也无法补回官方已清理且本地没有保存的历史。
